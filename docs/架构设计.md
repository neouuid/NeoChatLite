### 数据流向

#### 1. HTTP 请求流程

```
客户端 → API Gateway → 认证中间件 → 对应 Service → 数据库 → 响应
```

#### 2. WebSocket 实时消息流程

```
发送方 → 实例 A（持久化到 PostgreSQL）
              ├─ 本地投递：连在 A 上的接收方
              └─ Redis Pub/Sub → 实例 B → 连在 B 上的接收方
                                （Origin 标记避免二次转发）
```

#### 3. 音视频通话流程

```
呼叫方 → RTC Signaling Service → 信令交换 → WebRTC P2P 连接 → 通话
                 ↓
            保存通话记录
```

## 部署架构

### 单机 / 小规模（当前推荐）

```
            ┌─────────────────────────────┐
  浏览器/客户端 ──▶ │  neochat-app（单二进制）      │
            │   HTTP API + WebSocket      │
            └───────┬─────────────┬───────┘
                    │             │
        ┌───────────▼──┐   ┌──────▼────────┐
        │ PostgreSQL 16│   │ Redis 7       │
        │ (主库)       │   │ 缓存 + 跨实例广播 │
        └──────────────┘   └───────────────┘
                    │
        ┌───────────▼────────────────────┐
        │ 本地磁盘 uploads/（经鉴权接口访问）│
        └────────────────────────────────┘
```

`docker compose up -d` 即可起全套（Postgres + Redis + app），详见
[部署文档.md](部署文档.md) 与仓库根的 `docker-compose.yml`。

### 纵向扩展（多实例）

- 应用本身**无状态**，可以起多个实例放在反向代理后面
- 跨实例的 WebSocket 投递由 **Redis Pub/Sub** 完成（带 Origin 标记避免回环）
- 已知限制：登录失败计数与 IP 限流是进程内内存态，
  多实例时实际阈值 = 实例数 × 配置值，需要换成 Redis 计数

### 规划中（未实现）

- Kubernetes 编排、数据库读写分离、按 ID 分片
- 对象存储（当前是本地磁盘 + 鉴权下载接口）

## 客户端架构

### 客户端架构

```
┌──────────────────────────────────────────────────────────────┐
│                     Flutter（六端同一套代码）                  │
├──────────────────────────────────────────────────────────────┤
│  pages/          登录/注册、会话、聊天、通讯录、群信息、        │
│                  搜索、@我的、收藏、我的资料、他人资料          │
├──────────────────────────────────────────────────────────────┤
│  NeoChatSession（ChangeNotifier）                             │
│    · 登录态与用户资料     · 全部 API 操作封装                 │
│    · 离线同步游标         · 实时事件流                        │
├──────────────────────────────────────────────────────────────┤
│  client_sdk/dart（由 OpenAPI 生成）                            │
│    NeoChatApi → Transport（IoTransport / HttpTransport 条件导入）│
│    RealtimeClient → 连接器（dart:io / web_socket_channel）    │
├──────────────────────────────────────────────────────────────┤
│  本地存储：token_store（登录态）、message_cache（每会话 200 条）│
└──────────────────────────────────────────────────────────────┘
```

设计要点：

- **状态只有一处**：页面不持有 HTTP 客户端，全部经 `NeoChatSession`，
  使得状态逻辑可以在纯 Dart 单测里覆盖（26 个用例）
- **平台差异收敛在 SDK**：条件导入，业务代码里没有 `Platform.isXxx` 分支
- **鉴权 URL**：附件访问统一由 `session.fileUrl()` 拼 token

## 后端架构

### 结构：模块化单体

早期设计里画的是 6 个微服务共享一个库、靠 NATS 解耦——实际没有采用。
现在的后端是**一个二进制里的模块化单体**：

```
cmd/api-gateway      入口：配置 → 日志 → 数据库（含迁移）→ Redis → 路由 → 优雅关闭
internal/auth        注册/登录/令牌/刷新轮换/登录锁定/认证中间件
internal/user        用户资料、好友请求、黑名单
internal/chat        会话、消息、群组、收藏、@提及、上传、WebSocket Hub
internal/migrations  版本化迁移（goose + 双方言 SQL）
pkg/config           配置（默认值 + NEOCHAT_* 环境变量覆盖）
pkg/database         GORM 初始化（SQLite / PostgreSQL）
pkg/redis            缓存与 Pub/Sub
pkg/broadcast        跨实例广播（Redis 实现 + 本地降级）
pkg/middleware       限流、安全响应头、指标
pkg/response         统一响应信封
pkg/utils            JWT、密码哈希、日志
```

选择单体的理由：

- 模块边界清晰（auth / user / chat），但共享事务与连接池，
  聊天场景里「发消息 + 更新未读 + 写提及」天然要跨模块写库
- 部署与调试成本低：一个二进制、一份配置、一套迁移
- 需要拆分时，`internal/*` 已经按领域分开，迁移路径存在

### 请求处理链路

```
路由 → CORS / 指标 / 安全响应头
     → 认证中间件（JWT，校验 typ=access）
     → Handler（参数校验、取 user_id）
     → Service（业务规则、缓存失效、广播）
     → Repository（GORM）
     → PostgreSQL / SQLite
```

WebSocket 走单独的 `WebSocketAuthMiddleware`（额外接受 `?token=`），
连接上的读写分别由 ReadPump / WritePump 负责，带 ping/pong 与连接数上限。

## 关键选型记录

### 客户端框架：Flutter

早期方案评估过 React Native，最终落地为 Flutter，理由：

| 维度 | 结论 |
|---|---|
| 六端覆盖 | Flutter 一套代码覆盖 Android/iOS/Web/macOS/Windows/Linux；RN 桌面端需额外适配 |
| 与现有代码的结合 | 客户端只依赖 OpenAPI 生成的纯 Dart SDK，Flutter 可直接复用 |
| 可测试性 | 状态层是纯 Dart（`ChangeNotifier`），无需 widget 即可单测 |
| Web 支持 | 通过条件导入 `package:http` 跑通，已用真实 Chrome 验证 |

> 音视频通话（WebRTC）在早期评估里是 RN 的优势项，但本项目最终决定
> **不做通话**，该理由随之失效。

### 实时消息：单机 WebSocket + Redis Pub/Sub

- 不使用消息队列（NATS）持久化：消息先落 PostgreSQL，再由 WebSocket 推送，
  离线由 `/chat/sync` 游标补拉
- 多实例通过 Redis Pub/Sub 转发，中间带有 Origin 标记避免回环

### 状态管理：ChangeNotifier

对比过引入状态管理库（Riverpod/Bloc），最终用 Flutter 内置的 `ChangeNotifier`：
当前状态规模（一个 session 类 + 若干页面局部状态）不需要额外的框架，
且纯 Dart 实现让单测不需要 widget 环境。

## 安全架构

> 本节按**当前实现**描述；标为「未实现」的是规划而非现状。

### 认证与令牌

- **JWT（HS256）**：强制校验签名算法；令牌带 `typ` 声明区分 access / refresh
- **双令牌**：access（默认 1 小时，无状态）+ refresh（7 天，**服务端落库**）
- **刷新轮换**：refresh 一次性使用，每次刷新吊销旧记录并签发新令牌；
  重放已用令牌视为泄露，吊销该用户全部 refresh token
- **主动失效**：登出、改密码、重置密码都会吊销该用户全部 refresh token
- **登录防护**：同标识连续失败 5 次锁 15 分钟；认证接口按 IP 限流；
  生产环境弱 JWT 密钥（默认值或短于 32 字符）拒绝启动
- **密码**：bcrypt 哈希，注册/改密/重置统一 8~72 字节策略

### 文件访问

- 上传文件**不通过静态目录暴露**，统一走 `GET /api/v1/files/*path`
- 必须带 `Authorization` 或 `?token=`；文件被消息引用时还要求是会话成员
- 路径穿越防护：拒绝 `..`、绝对路径、盘符，拼接后二次校验仍在 uploadDir 内

### 传输与接口

- **CORS**：按配置的 allow_origins 白名单
- **安全响应头**：`X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`、
  `Permissions-Policy`；TLS 终结于本服务时下发 HSTS
- **WebSocket**：单帧 4 KB、服务端 25s ping、60s pong 超时、单用户 5 连接、全局 20000 连接上限
- **SQL 注入**：全部走 ORM 参数化查询

### 未实现（规划）

- 静态数据加密、手机号/邮箱脱敏存储
- TLS 在应用内终结（当前由反向代理负责）
- 多端设备管理界面（`devices` 表已存在，无接口）

## 性能优化策略

### 客户端优化

- **虚拟列表**: 长列表使用 FlatList 优化
- **图片缓存**: react-native-fast-image
- **状态持久化**: MMKV 高性能存储
- **懒加载**: 路由懒加载
- **内存优化**: 及时清理不必要的状态

### 后端优化

- **数据库索引**: 合理的索引设计
- **查询优化**: 避免 N+1 查询
- **缓存策略**: Redis 热点数据缓存
- **连接池**: 数据库连接池
- **异步处理**: 耗时操作异步化

## 可扩展性设计

### 水平扩展

- **无状态服务**: 所有服务无状态，可水平扩展
- **数据库分片**: 用户数据按 ID 分片 (远期)
- **读写分离**: 数据库读写分离 (远期)

### 拆分可能性

`internal/*` 按领域分好了，但**当前不做微服务**：
聊天写入天然跨模块（消息、未读、提及、会话活跃时间），
拆开后会立刻需要分布式事务或补偿逻辑，收益远小于成本。
若将来某些模块（如文件、搜索）成为瓶颈，可以单独拆出。
